# 仓库与协议

仓库存放已经写好的包。核对签名仍是 `files.unseal` 和 `files.verify`，因为信任的公钥在取出的那一侧，不在存放的那一侧。仓库若代为核对，就要替调用方决定哪把公钥可信，存放和信任就绑在同一台机器上。

`lib` 描述这一份包：名字、版本、清单。`repo` 按「名字/版本」放下许多份。`mods` 记在清单里，供读清单的人使用。仓库不按 `mods` 去找脚本，否则存放处就要理解脚本布局。`depends` 同样只是清单里的 `"名字 版本"`。取回时由脚本再调用 `repo.fetch`，这样一次取出不会变成沿着依赖图的递归下载。

`dake.key` 留在作者的输出目录。共享密钥和私钥只在签名的机器上。协议若收发这把密钥，存放处就变成密钥的副本。公钥和 `dake.seal` 可以放在包旁边，因为它们本来就是给取出方核对的。

协议走已经有的 `url` 和 `serve`。路径和正文是固定的，任何 dake 都能对任何仓库说话，不必再约定一套路由行为。这和 Git 的智能 HTTP 一样：用现成的 HTTP 和 TLS，不另开一种端口。监听、证书和并发仍是这条 `url` 上的设置。没写 `serve` 里的 `repo 地址名` 时，`/dake/v1/` 没有特殊含义。

上传先清单、后文件、最后提交。清单定下名字、版本和每个文件的哈希，文件才能对照这份清单落盘。提交失败就删掉暂存，已提交的目录不被半份上传替换。GET 只读改名完成的目录，所以读到的要么是完整的一份，要么是没有。

自动放入发生在 `out_dir` 写完之后，不等 `files.seal`。同一次运行里，签名若写在包目录出现之前，签的就不是这份包。签名留成对已有目录的另一次调用，放入和签名的顺序才不会缠在一起。
